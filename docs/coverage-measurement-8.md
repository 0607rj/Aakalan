# Coverage measurement: 8 back-test tenders, manual reading vs the app's reading

Measurement only (2026-10-23 to 2026-10-24). No code, parameters, rate card, goldens or back-test
were changed, nothing was re-priced, and nothing here is a proposed fix.

**Code path for reading B.** The production path, unchanged: `parse_document` → `ai_read`
(prompts `extract_tender_v8` + `gap_check_v3`) → `verify_findings` (citation check) →
`merge_extractions`, driven by a local relay script. The one difference from production is the
model call: each request the code would send to the AI provider was written to a file and answered
by a Claude Sonnet subagent in Claude Code (a **stand-in**, not the Anthropic API and not the
production model). Same code path, same prompts and schema validation, different model.

**Reading A.** A separate manual reading (a Claude Code subagent, no access to B) of each tender's
full text, cover to cover, blind to prices (amounts blanked; pages where an amount slipped through
are listed below and no amount was written down). One entry per distinct requirement, each with
clause, file, page and a verbatim quote under 15 words.

**Comparison.** Each A requirement was marked **both** (a B item covers it), **broad** (only a
coarser B item covers it) or **A only**, with one reason per miss. "Priced" means the A categories B
is designed to price: functional, integration, report, hosting, support, SLA, manpower, training,
migration.

## Pattern

The misses do **not** cluster on tables, images or late pages:

| Where the A item sits | A items | A only | Miss rate |
|---|---:|---:|---:|
| Table row | 598 | 133 | 22% |
| List item | 918 | 220 | 24% |
| Running prose | 309 | 109 | 35% |
| Form / annex | 8 | 7 | 88% |
| Last third of its file | 254 (13.8% of all) | 66 (14.1% of misses) | 26% |

Table rows are missed no more often than list items, and late pages carry the same share of misses
as of requirements. No file needed OCR, apart from one empty one-page scan (iob-website att07). The
only file refusal (a spreadsheet, as designed) held no requirements. Every long file (up to 158
pages) went to the model in one request.

Two different things are going on:

- **Most misses (77%) are by design.** They are kinds of item the prompt and schema never collect,
  and they would be missed by any model on this path. For the priced ones among them (support
  detail, response and restore times, extra staff roles, training) this is a gap in what B records,
  not an extraction failure.
- **The rest (about 20%) are scattered over ordinary prose and lists, with no page or format
  pattern.** These are fine-grained items kept at feature level or left out. Because they have no
  structural pattern, they are more likely the stand-in model's summarising (the call-path
  difference) than a real weakness of the pipeline. One real but small weakness shows: late-page
  BOQ and financial-bid tables in the two CPCB tenders (cpcb-ewaste, cpcb-tyre), where B did not
  use the BOQ rows, so their staff numbers came out only broad or missing.

## Method notes and deviations

- **B readers were told** to read every request in full, to answer only from the request, and not to
  check their own quotes with scripts.
- **cpcb-battery:** the first B reading wrote 9 empty gap checks after too few reads. It was asked
  to redo them, reading each request in full, and they were still empty, with reasons.
- **iob-chatbot:** the B reader checked its quotes with a script (against the brief) and shortened
  one quote that ran across a page break.
- **cpcb-tyre:** the B reader read att12's gap-check request only in part, relying on a diff against
  a request it had already read.
- **iob-trade:** the B reader did not re-read a second gap-check request that was identical to one
  it had read.
- **cpcb-ewaste:** the B reader wrote att01's first reply after reading lines 1-1900, then read the
  rest. The reply did not change.
- **iob-website:** att07 (an empty one-page scan) got no gap check, because the relay did not ask
  for one.
- **Comparison readers took two values from the raw `merged.json`** that the money-masked view
  leaves out. The performance-guarantee percentage was counted as covering A's
  performance-security item: broad in cpcb-ewaste and cpcb-tyre, both in iob-trade. `not_priced`
  was also read from `merged.json`.
- **B duplicates unclear points across files,** and GeM-form files raise "scope not in this
  document" unclear points. These are counted in "B items" above.
